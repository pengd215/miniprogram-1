# 客户端首页、多 Tab 与购物车下单实施计划

> 基于《客户端购物车与下单方案.md》整理。目标版本：v1.3.x；当前仅为实施计划，不代表功能已经开发或部署。

## 目标与边界

将客户角色从单一报价查询扩展为四个客户端入口：**首页、查询、购物车、我的**，形成“浏览商品 → 查看详情 → 加入购物车 → 提交订单意向 → 业务员跟进”的闭环。

首版采用线下定金/业务员确认，不接微信支付，不在客户提交订单时扣减库存。首版订单应明确标注为“待业务员确认”，不承诺库存锁定或订单自动成立；业务员确认库存、价格和线下定金后再推进订单状态。库存预占、在线支付和售后退款分别作为后续独立能力评估。

## 对原方案的可行性调整

1. **先补服务端读边界，再做商品展览。** 当前 `pages/client/search.js` 直接对 `products` 调用 `watch()`，这会绕过 `clientSearchQuote` 的字段投影。应移除客户端集合监听；客户可见商品统一由云函数返回，并在服务端按客户身份校验、过滤草稿/软删除记录及投影字段。
2. **价格与库存状态由服务端重新校验。** 加入购物车时可返回展示快照，但快照不能作为结算依据。提交订单时服务端重新读取商品、核实状态及价格并计算金额；若价格变化，返回变化明细要求客户再次确认。无库存预占时，订单是意向单，必须向客户说明库存以业务员确认为准。
3. **客户身份只从云函数上下文取得。** 不接受客户端传入的 `_openid`、`customer_id`、角色、单价、总价、定金或订单状态作为可信数据；每个购物车/订单云函数均在服务端验证 OpenID 对应员工账号仍启用且角色为 `customer`。
4. **采用独立客户端自定义导航。** 员工端继续使用现有全局 `tabBar`，客户端使用自定义 `client-tabbar`，不将客户页面加入员工端原生 TabBar。导航封装成一个组件并统一处理当前项与购物车角标。切换根 Tab 可用 `reLaunch` 防止页面栈累积；需要保留搜索词时由页面缓存恢复，不依赖隐藏页面栈。
5. **分离订单提交和外部通知。** 订单写入成功后不能依赖单次 webhook 调用作为事务一部分。先持久化订单，再异步通知；通知失败保留待重试状态，订单不能因此丢失或重复创建。
6. **暂不以“付定金”作为首版必需步骤。** 线下转账阶段由业务员人工核实到账并推进状态。小程序不可让客户自行把定金标记为已支付。

## 建议的数据模型

### `carts`

一条文档代表某客户购物车中的一个商品。建议用服务端生成的稳定文档 ID（客户 OpenID 与商品 ID 的组合摘要），并为 OpenID、商品 ID 建索引，减少重复加入产生并发重复行的可能。

建议字段：`_openid`、`customer_id`、`product_id`、`quantity`、`display_snapshot`、`create_time`、`update_time`。客户端不得直接读写集合；所有读写由 `cartManage` 云函数执行。商品删除、下架或档案未完善时，购物车行保留但标为不可结算，不能悄悄消失。

### `orders`

建议字段：`order_no`、`request_id`、`_openid`、`customer_id`、`customer_name`、`items`（商品字段和价格快照）、`total_amount`、`deposit_amount`、`deposit_status`、`status`、`contact`、`remark`、`create_time`、`update_time`、`notification_status`。金额统一由服务端根据数据库价格和数量计算；避免用客户端传值或浮点数累加作为订单金额。

订单建议状态：`submitted`（客户已提交，待业务员处理）→ `awaiting_deposit`（待线下定金）→ `deposit_confirmed`（业务员已确认到账）→ `processing` → `completed`；另设 `cancelled`。所有状态变更由有权限的员工云函数执行，并记录操作人、时间和原因。

首版不建议额外创建 `order_items` 集合，订单明细快照可先放在订单文档中；若后续单笔商品数、订单量或查询统计需要，再拆分明细表。

## 分期实施

### P0：安全与数据规则基线

**范围**

- 梳理 `products` 的可售条件：草稿状态字段、软删除字段、图片字段及历史数据缺省值。
- 为客户端查询建立服务端统一校验，确认调用者为启用状态的客户角色。
- 移除 `pages/client/search.js` 对 `products` 集合的直接 `watch()`；查询只经过云函数。
- 给现有 `clientSearchQuote` 加身份校验、可售状态过滤、分页/查询限制和字段白名单。
- 修正现有查询页事件绑定与云函数数据契约不一致的问题（例如模板绑定了缺失的详情处理函数时，点击会无效）。
- 决定价格变化规则、可售状态、订单意向和库存未预占的提示文案。

**验收**

- 客户无法通过小程序直接读取成本、库位、预警值等内部字段。
- 草稿、软删除、下架/不可售商品不会出现在客户端。
- 未登录、停用账号、非客户角色调用客户查询接口均被服务端拒绝。
- 现有客户搜索通过真机验证，员工端功能无回归。

### P1：客户端 Tab 框架、首页展览和商品详情

**范围**

- 新增 `client-tabbar` 自定义组件及 `home`、`detail` 页面，并将客户登录后的默认路由改为首页。
- 首页使用双列商品卡片，服务端分页，每页建议 8 条；仅展现可售且有有效图片的商品。提供无图/无数据/加载失败状态、下拉刷新和触底加载。
- 新增 `clientListProducts` 云函数的 `showcase`、`detail` 查询动作；共享 P0 的身份校验和可售过滤。
- 商品详情展示图片、车型、年款、方向、OE 编号和报价；不展示库存、成本、库位等内部信息。
- `立即下单` 暂时不开放，等 P2/P3 的结算闭环就绪后再显示。

**验收**

- 客户登录落到首页，四个 Tab 可切换，员工端全局 TabBar 未改变。
- 分页无重复/漏项，切换 Tab 后不会无限增长页面栈；图片为空、失效或加载中均有稳定占位。
- 首页和详情的接口只返回白名单字段；不可售商品的详情请求失败关闭。

### P2：购物车和加购

**范围**

- 新增 `cartManage` 云函数，支持列表、计数、加购、数量修改、删除和选中状态更新；商品与客户身份均由服务端核实。
- 新增购物车页，处理数量边界、已下架/已删除商品、价格变化提示、空购物车和网络失败。
- 首页、查询结果、详情页均可加入购物车；统一更新 Tab 角标。
- 为数量更新与同商品重复加入设计幂等/并发策略；避免前端重试造成数量翻倍。

**验收**

- 同一客户同一商品只显示一行；快速重复点击或网络重试不重复增加数量。
- 不同客户购物车互相隔离；客户不能修改其他人的购物车。
- 数量为正整数并有业务上限；无效或不可售商品不能进入结算清单。
- 角标在冷启动、页面切换、加购、删除后能从服务端状态恢复。

### P3：订单意向提交、订单列表和详情

**范围**

- 新增 `submitOrder` 云函数和 `orderManage` 客户查询动作；提交时由服务端重读商品、核对价格/状态、校验数量并重新计算总额。
- 使用客户端生成的 `request_id` 做幂等，避免超时重试生成多个订单。
- 创建订单与清理已提交购物车项采用事务；如 CloudBase 事务/操作限制不适合跨集合大批量处理，应先创建订单并用订单 ID 标记购物车项已结算，保证可恢复，不能先删购物车再写订单。
- 新增确认页、提交结果页、我的页和我的订单列表/详情；收货联系人与联系方式仅采集业务必需字段。
- 商品价格在加购后发生变化时，提交接口返回变化项，要求客户回到确认页再次确认。
- 当前不扣库存，不接受客户传入价格/定金比例/订单状态；订单提示为待业务员确认。

**验收**

- 多商品订单金额由服务端重算；伪造总额、价格、用户 ID 或状态的请求不会影响订单。
- 同一 `request_id` 重试只得到同一订单结果。
- 创建订单失败时购物车明细仍可恢复；订单成功后只清理本次选中商品。
- 客户只能查询自己的订单；客户不能自行确认定金或改变订单状态。
- 订单状态流转合法，用户看到明确的“待确认/库存以业务员确认为准”说明。

### P4：员工订单处理与可靠通知

**范围**

- 为员工新增订单列表、订单详情和受权限控制的状态变更接口；在首页显示待处理数量/红点。
- 业务员确认订单内容、库存、价格和线下定金到账后推进订单状态；所有变更写审计信息。
- 先实现小程序工作台待办为可靠主渠道；企微机器人作为可选通知渠道，密钥只存云函数环境变量。
- webhook 通知异步发送，保存发送状态、失败原因与重试次数；禁止在订单写入事务中等待外部网络请求。

**验收**

- 只有授权员工能处理订单；客户和普通未授权角色无法调用状态变更。
- 待办数量与订单状态一致；重复通知不会重复生成订单或重复推进状态。
- 通知失败可重试，失败不丢订单；可以查询通知处理结果。

### P5（可选）：微信支付定金与消息通知

**前置条件**

- 已有可用微信支付商户号、商户 API 证书/密钥、正确的小程序 AppID 绑定和支付回调域名/云函数配置；完成退款、对账和财务流程确认。
- 明确定金比例或固定金额规则及订单取消/退款策略。

**范围与验收**

- 服务端创建支付单并计算金额，客户端只发起支付；服务端验签支付回调并幂等更新支付状态。
- 只有可信支付回调可把定金标记为已支付；提供退款和异常支付对账流程。
- 订阅消息仅在获得用户授权后发送，发送失败不改变订单状态。

## 版本交付建议

- P0 与 P1 可作为第一批发布：客户能安全浏览首页、查找商品并查看详情。
- P2 单独发布：完成商品加购和购物车维护。
- P3 发布后才开放“提交订单”，组成客户侧下单意向闭环。
- P4 完成后形成业务员承接与状态跟踪闭环。
- P5 独立评估，不阻塞前四期上线。

每期先在测试云环境部署，使用客户、停用客户、员工和管理员账号做权限测试；再验证分页、重复提交、弱网重试、商品下架/价格变化、购物车跨账号隔离和员工端回归。每期验收通过后再合入主分支并部署生产。
